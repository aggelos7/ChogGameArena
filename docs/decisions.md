- DEC-012 (2026-10-09, STORY-009 — confirmed, PR #73): Guest persistence. A guest is a `Player` row with a server-generated id; the browser holds an opaque 256-bit session token in an HttpOnly, SameSite=Lax (Secure outside local dev) cookie; the database stores only its SHA-256 hash. Sessions last 90 days, sliding on use (renewal persisted at most daily); expired or revoked sessions get a new guest. Recovery works only in the same browser while the cookie exists. Guest-to-wallet linking/merging remains DEC-004.
- DEC-013 (2026-10-09, STORY-009 — confirmed, PR #73): Same-site hosting for web and API. In staging and production the Angular app and the API must be served from the same registrable domain — e.g. `app.<domain>` + `api.<domain>`, or the API reverse-proxied at `<domain>/api`. Never a shared-suffix host such as `*.pages.dev` for one and a custom domain for the other. Rationale: guest (and later wallet) sessions use an HttpOnly `SameSite=Lax` cookie, which is the CSRF protection; a cross-site deployment would require `SameSite=None`, anti-forgery tokens and strict CORS, and is exposed to third-party-cookie blocking. Impact: E07 staging/production hosting stories, SignalR authentication. Revisit only if a cross-site deployment becomes unavoidable, together with adding anti-forgery tokens.

  - **On-chain facts (read-only probe, 2026-10-10):** supports ERC-721 and Metadata, not Enumerable; token ids 1–1969 (0 and 1970 revert); about 1,000 holders.
  - **Metadata:** `tokenURI` points to `ipfs://…` JSON with 12 traits and a `.webp` image. Metadata handling is STORY-016.
  - **Ownership adapter:** a JSON-RPC client written in-house, with no indexer and no new dependency.

- DEC-014 (2026-10-09, STORY-012 — confirmed by product owner): Wallet connection and supported network. The web app talks to wallets through the browser standards EIP-1193 and EIP-6963 directly, with no wallet SDK dependency; it covers extension and in-app-browser wallets. WalletConnect (deep links/QR to mobile wallet apps) needs a hosted project id and is deferred to a separate decision. Parameters were taken from docs.monad.xyz on 2026-10-09. The NFT contract and chain for ownership checks remain DEC-001. A connected address is display state only; wallet sign-in is STORY-013.
- DEC-015 (2026-10-10, STORY-013 — confirmed by product owner): Wallet sign-in binding and verification.
  - **Sign-in binding** (the sign-in part of DEC-004):
    - A verified wallet that isn't bound to anyone upgrades the caller's current guest to a wallet player (same id, name, avatar and stats).
    - A wallet already bound to a player signs in as that player; the caller's guest is left unchanged, with no history merge.
    - A caller who is already a wallet player and signs in with a different wallet gets a separate player for it.
    - One wallet per player, enforced by a unique `Players.WalletAddress` column. Merging existing histories remains DEC-004.
  - **Session:** every sign-in replaces the session and revokes the old cookie. Sign-out revokes the session, and the browser continues as a new guest.
  - **Verification:**
    - The challenge is an EIP-4361 message built by the server from configuration (`WalletAuth:Domain`/`Uri`, the configured chain id), with a 128-bit single-use nonce and a 5-minute expiry. It's bound to the requesting session's player.
    - Each challenge is consumed atomically by the first verification attempt, successful or not.
    - The signer is recovered from the stored message with EIP-191, secp256k1 and keccak-256. High-s signatures are rejected.
  - **Wallet types:** only regular (EOA) wallets are supported. Smart-contract wallets (ERC-1271) fail safely and can be added later with an RPC check.
  - **New dependency:** BouncyCastle.Cryptography 2.7.0 (MIT), for keccak-256 and secp256k1 only; recovery is our code, tested against published vectors.
- DEC-016 (2026-10-10, STORY-016 — confirmed by product owner): NFT metadata source and stored ownership.
  - **Gateway:** metadata and images are read through IPFS gateways from configuration (`Nfts:Ipfs:Gateways`), tried in order. The default is Pinata's public gateway. On 2026-10-10 it was the only public gateway still serving the collection: ipfs.io and dweb.link answer 429, cloudflare-ipfs is gone, and the others redirect to those. A dedicated gateway can be added via secrets, with no code change. Only `ipfs://` URIs are followed and redirects are not, so the collection can't direct server requests to other hosts.
  - **Fetching:** metadata is fetched on demand, when a wallet's tokens are listed or checked, within a per-request time budget. It's stored and read again weekly; outages are retried after 5 minutes. There's no background prefetch job.
  - **Outage fallback (NFT-003):** listing may use a wallet's stored scan for up to 10 minutes while the chain can't be read. Match admission (single-token checks) always reads the chain.
  - **Metadata facts:** names are those of the shuffled metadata files, e.g. token 1 is "CHOG #1462". There are 12 traits (Background, Base, Skin, Side, Body, Mouth, Eyes, Head, Accessory, Form, Tier, Naked) and a `.webp` image of about 300 KB.
  - Image hosting and artwork rights remain DEC-005.
- DEC-017 (2026-10-11, STORY-017 — confirmed by product owner): Character gallery and preferred character.
  - **Standard Chogs (NFT-005):** the built-in profile avatars (`classic`, `mint`, `sunset`, `ocean`, `berry`, `gold`) double as standard Chog characters for everyone, holders included. They're drawn from their colour until artwork is approved (DEC-005); there is no separate catalogue.
  - **Preferred character:** the gallery saves one choice per player on the server (`PUT /api/characters/selected`). An NFT choice needs a wallet player and a live `ownerOf` check; a refused choice changes nothing. It's a preference only: ownership is verified again and the character locked at match start (STORY-018, NFT-008/009).

- DEC-019 (2026-10-11, STORY-018 — confirmed by product owner): Character check at match start.
  - **Outage:** if NFT ownership can't be read when a match starts, the player can't start with that NFT; there is no silent switch to a standard Chog. They can choose a standard Chog and play right away. This follows NFT-008: ownership is verified before start.
  - **Unowned NFT:** the start is refused (`NftNotOwned`) and the player chooses again; the saved choice isn't changed by the check.
  - **Storage:** the immutable `CharacterSnapshot` is built now. It is stored with the match player record when matches exist (STORY-023/028); there is no separate table.
- DEC-020 (2026-10-11, STORY-019 — confirmed by product owner): Game registry and room codes.
  - **Registry:** supported games are rows in a `GameDefinitions` table seeded by reviewed migrations (`chog-life`, `chog-race`, 2–6 players), so rooms reference them with a foreign key. Whether a game is enabled stays in the `Games:Items` configuration; a room needs both.
  - **Room codes:** 6 characters from 31 letters and digits without look-alikes (no 0, O, 1, I or L), about 887 million codes, drawn with cryptographically secure randomness. Uniqueness is a database index; a collision draws another code.
  - **Hosting:** a player may host one `Waiting` room at a time (filtered unique index). Rate limits come with the room API (STORY-020).
- DEC-021 (2026-10-11, STORY-020 — confirmed by product owner): Joining rooms.
  - **One open room per player:** a player who is in a `Waiting` room, as host or member, can't create or join another; the refusal names that room. An `Active` match the player is still in blocks this too (DEC-025).
  - **Rejoining:** joining a room you're already in succeeds and changes nothing, so invite links and double taps are safe.
  - **Errors:** problem details with a stable `code`: `unknown_game` (400), `room_not_found` (404, also for malformed codes and for rooms the caller isn't in), `game_unavailable`, `already_in_room`, `room_full`, `room_started`, `room_closed` (409).
  - **Web:** a minimal create/join screen and room page; members appear on refresh until live updates (STORY-022).
- DEC-022 (2026-10-11, STORY-021 — confirmed by product owner): Lobby and ready state.
  - **Abilities:** the lobby shows an ability placeholder only; ready does not need an ability until STORY-033 adds the choice.
  - **Start:** host only, with the game's minimum to capacity of members, all ready. Every member's Chog is checked live (STORY-018): a member whose NFT is no longer owned is set back to not ready and nothing starts; if ownership can't be read nothing changes and the host retries. Then the room becomes `Active`. The character snapshot and match record are kept from STORY-023/028.
  - **Host ready:** everyone, the host included, must mark ready.
  - **Changing Chog:** ready counts only for the Chog selected when marking ready, so choosing another Chog makes the player not ready. Joins and leaves don't change anyone else's ready status.
  - **Errors:** `not_host` (403), `not_enough_players`, `players_not_ready`, `character_unavailable` (409), `ownership_unavailable` (503), plus the room codes of DEC-021.
- DEC-023 (2026-10-12, product owner): Leaving a waiting room is STORY-063. A member who leaves frees their seat and their one open room. A host who leaves cancels the room for everyone; hosting is not passed on. Leaving an active match is a forfeit (DEC-025).
- DEC-024 (2026-10-12, STORY-022 — confirmed by product owner): Live room updates.
  - **Hub:** one SignalR hub at `/api/hubs/rooms`, WebSockets only, authenticated by the session cookie. A connection subscribes to a room only after the server checks membership; unknown codes and rooms the caller isn't in both fail with `room_not_found`. Players who leave are taken out of the room's group, so messages reach members only.
  - **Payload:** the server sends only `RoomChanged(code)`; clients fetch `GET /api/rooms/{code}`, which stays the one source of room state. Versioned snapshots and resync come with STORY-026. **Superseded by DEC-028:** the hub now pushes snapshots.
  - **Commands:** room changes stay REST endpoints; the hub offers no game commands until STORY-024.
  - **Web:** the lobby follows the room live; Refresh is offered only while live updates are down.
  - **Dependencies:** `@microsoft/signalr` (web, pinned exactly; its Node-only transitive packages are not bundled) and `Microsoft.AspNetCore.SignalR.Client` (backend tests only) are approved.
  - **Scale:** subscriptions are tracked in memory, so one API instance; several need a backplane and shared tracking (ADR-010).
- DEC-025 (2026-10-12, STORY-023 — confirmed by product owner): Match lifecycle.
  - **States:** `Waiting`, `Active`, `Completed`, `Cancelled`, `Abandoned`. The allowed transitions are Waiting → Active (the host starts), Waiting → Cancelled (the host leaves), Active → Completed (the game finishes, set by game rules in later stories) and Active → Abandoned (fewer than two players remain). Completed, Cancelled and Abandoned are final. Any other transition is refused, and nothing changes. `Cancelled` always means a room that never started; `Abandoned` means a match that started and ended early.
  - **One open room:** a player who is in a `Waiting` room, or who is playing in an `Active` match, can't create or join another room (`already_in_room`, extending DEC-021).
  - **Leaving a started match is a forfeit:** the player keeps their seat record and character snapshot, is marked as left, and is free to play elsewhere. They can still read the room but don't get its live updates and can't rejoin. The match continues while two or more players remain; otherwise it becomes `Abandoned`. Once the match starts, the host has no special role, and the host leaving doesn't end the match.
  - **Character snapshot:** the snapshot taken at start (DEC-019) is stored on each room member, which is the match player record. It's saved in the same transaction as the start, and the room shows each member's locked Chog from then on.
- DEC-026 (2026-10-12, STORY-024 — confirmed by product owner): Match commands.
  - **Engine only:** the command pipeline (envelope, versioning, deduplication, stale checks) plus a per-game rules interface. No game registers rules yet, so every command type is `unknown_command` until Chog Life and Chog Race plug in (DEC-002, DEC-003).
  - **Transport:** REST, `POST /api/rooms/{code}/commands`, with problem-details codes, the room rate limit and cookie auth. The hub stays notify-only (DEC-024).
  - **Retries:** a command with an `actionId` already processed in the match returns `200` with the first attempt's result and the current version, marked `replayed`. Reusing an `actionId` with a different type or payload, or by another player, is `409 action_conflict`. Rejected commands aren't recorded; retrying one is evaluated again.
  - **Version:** one room-wide `version`, bumped by every committed change (join, ready, leave, start, completion and each accepted command). The room response returns `matchId` (the room's UUID) and `version`. A command whose `expectedVersion` isn't the current version is `409 stale_version`, so a forfeit or any other change makes older commands stale.
- DEC-027 (2026-10-12, STORY-025 — confirmed by product owner): Turns and the AFK timer.
  - **Order:** players take turns in join order, the host first, fixed as seats at the start; players who left are skipped. **Superseded by DEC-031:** seats are now drawn in a secure random order.
  - **Authority:** the engine owns the current player, turn number and deadline; only the current player's commands reach the game's rules (`not_your_turn`), and not after the deadline (`turn_expired`). The rules say which accepted command ends the turn.
  - **Timeout:** configurable (`Matches:TurnTimeout`, default 20 seconds per ENG-007), fixed per match at its start. An in-process scheduler times out an overdue turn exactly once under the room lock: the game's safe default is applied, or the turn is skipped.
  - **Repeated AFK:** a player whose turn runs out 3 times in a row (`Matches:MaxMissedTurns`) forfeits, as if they had left; acting resets the count. A match left with fewer than two players is `Abandoned`, so an all-idle match ends by itself.
  - **Restart:** deadlines are stored; turns that ran out during downtime time out on the first check after start, and the next turn gets a full timeout. **Superseded by DEC-030:** a restart now gives the current player a full new turn.
- DEC-028 (2026-10-12, STORY-026 — confirmed by product owner): Realtime state synchronization.
  - **Push:** after every committed change the hub sends each subscribed member `RoomUpdated(room)`: their own complete snapshot, the same `RoomResponse` that `GET /api/rooms/{code}` returns, read after the commit and tagged with the room's `version`. It replaces `RoomChanged(code)` (DEC-024), so a change no longer costs every viewer a `GET`.
  - **Convergence and gaps:** clients keep the snapshot with the highest version, from pushes and REST answers alike, and ignore older ones arriving late. Each snapshot is complete, so a skipped version needs no replay. `SubscribeRoom` returns the current snapshot, so a client that missed versions while disconnected resyncs by subscribing again, which every reconnect does.
  - **Recipients:** chosen per connection from the subscription registry; SignalR groups are no longer used. Only players still playing in the room when it is sent get an update. A player who forfeits gets one last snapshot showing them out; a member who leaves a waiting room gets nothing more.
  - **Game state (ENG-013):** snapshots include `state`, the game's state as the player may see it, from `IMatchRules.ViewFor`. A game without rules never shows its state. Each game hides its own private information (hands, upcoming cards).
- DEC-029 (2026-10-12, STORY-027 — confirmed by product owner): Disconnect and reconnect.
  - **Finding the game again:** `GET /api/rooms/current` returns the player's open room (a waiting room they're in, or a started match they still play), or `204`. The web shell shows a "Return to game" / "Back to room" banner on every page except that room's own page, checked again after each navigation and whenever the player changes. The session cookie is the identity, so a refresh, a new tab or a reconnect is the same player; nobody else can take the seat (`room_not_found`, `room_started`).
  - **No extra turn:** a disconnected player's turn timer keeps running, with no pause or grace. Their turn times out with the game's safe default as usual (DEC-027), and 3 misses in a row forfeit. Reconnecting never changes the room, its version or the deadline.
  - **Client reconnect:** the web client never gives up. It retries at once, then after 2, 5 and 10 seconds, then every 15 seconds. It shows live updates as off after 3 failed tries, while retries go on. It retries at once when the browser comes back online or the tab is shown, and it subscribes again when a live tab is shown (a hidden tab may have been frozen). Only a refused subscription (`room_not_found`) stops it.
  - **Presence:** other players aren't shown who is disconnected; that may come in a later story.
- DEC-030 (2026-10-12, STORY-028 — confirmed by product owner): Match results and restarts.
  - **Restart policy:** active matches are restored, not ended. Every change was committed with its room, so the state, version, turn and players survive. When the API starts, before it takes requests, each active match's current player gets a full new turn from then, with no missed turn counted, because the downtime was the server's fault. The version is bumped, so commands built before the restart are stale. This replaces DEC-027's restart rule (a turn that ran out during downtime timed out and counted as missed).
  - **Results:** a game's rules finish a match with standings, a rank for every player still playing (1 = winner; ties share a rank and skip the shared places). The ranks are stored on each room member, the match player record, once, with the move to `Completed`. Players who left are ranked after those still playing, the latest to leave highest. There is no separate results table.
  - **Stats:** only a completed match counts. Every member, including those who left, gets one more game played, so leaving doesn't dodge a loss; each player ranked first gets a win. Abandoned matches have no winner and change no stats, so one of two accounts leaving can't farm wins.
- DEC-031 (2026-10-13, STORY-029 — confirmed by product owner): Server randomness and forged commands.
  - **Turn order:** at the start the server seats the players in a random order drawn with cryptographically secure randomness, so the host gets no first-move advantage. The order stays fixed for the match. This replaces DEC-027's join order, host first.
  - **Randomness:** game rules get the server's `IRandomSource` with each command and each timed-out turn, and draw every die, card, event and target from it. Production uses the operating system's secure generator; tests inject a scripted source. A payload carries only the player's choices; outcomes in it are ignored.
  - **Unauthorized commands:** commands from outsiders, for another match, in a room not started or closed, from a player who left, out of turn, after the deadline or on an old version are refused before the rules run. They change nothing and draw nothing. Ability commands get the same engine checks now; ability-specific checks (which ability, uses left) come with STORY-034.
- DEC-011: Adopt Nx for Angular workspace and frontend task orchestration; keep .NET 8 solution native, optionally wrapped by Nx run-commands. No Nx Cloud for MVP. No production topology changes.
- DEC-032 (2026-10-13, STORY-030 — confirmed by product owner): Ability catalog and execution contract.
  - **Catalog:** each game declares its abilities in versioned code in its module: id, name, description, target kind, activation windows, max uses (default 1) and numeric parameters such as `percent`. There's no database table or appsettings section. Any change to a definition bumps the catalog version, which STORY-033 snapshots at start (NFT-015). The catalog is checked when it's built: every definition has exactly one handler, ids are unique, and each definition configures exactly the parameters its handler declares, within range. A bad catalog stops the API at startup.
  - **Targets:** an ability that targets an opponent names them by seat (`{"abilityId": "card_steal", "target": 2}`), because player ids never reach clients. The target must be another player still in the match; an ability without a target must not name one. Seats are added to room snapshots when the first targeted ability ships (STORY-034/055).
  - **Execution:** `AbilityEngine` (Core) uses an ability by id. It checks, in order, that the player is still in an active match, the payload (only `abilityId` and `target`), the ability in the game's catalog, the target, then the game's current activation window, then the game's own conditions, and only then applies the handler's effect. Every refusal has a stable code and changes nothing, draws nothing and never reaches the effect. Handlers see players only as ids and seats, never characters or NFT traits.
  - **Scope:** this story is the Core contract only. `USE_ABILITY` doesn't go through the engine yet; the selected-ability check, usage counting and routing come with STORY-033/034.
- DEC-033 (2026-10-13, STORY-031 — confirmed by product owner): Shared ability pool.
  - **Strategy:** `IAbilityAssignmentStrategy` (Core) decides which of a game's abilities a player may choose from with their character. `SharedAbilityPoolStrategy` is the only one: every player, guest or NFT holder, gets the game's whole catalog, and the character (with its traits) is never read. It is fixed in code, with no configuration setting; a future trait-based strategy replaces the one registration without engine or game changes.
  - **Pool:** `AbilityPool` (Core) is what callers use. It returns the strategy's answer in catalog order, limited to the game's catalog: abilities the game doesn't define, duplicates and altered copies are dropped, and each ability is the catalog's definition. A game without a catalog offers nothing; `Offers` refuses unknown or malformed ids.
  - **Scope:** server-side only. There's no API change; STORY-033 shows the pool in the lobby and checks the selection with it.
- DEC-034 (2026-10-13, STORY-032 — confirmed by product owner): Trait-ready metadata boundary.
  - **Scope:** contracts only. Core gets `TraitSet` (normalized traits) and `ITraitAbilityResolver`, the contract a future trait-based strategy is built on. There's no production resolver or trait-based strategy, and DI still registers only `SharedAbilityPoolStrategy` (AGENTS.md: no TraitBased until requested). Tests use a test-only trait strategy to show that swapping the one strategy registration changes nothing in the engine, the pool or the games.
  - **Normalization:** for matching, each trait type and value is trimmed, inner whitespace is collapsed to one space and both are lower-cased (invariant), so `Rarity: Legendary` and `rarity :  legendary` are the same trait. Duplicates are removed and the set is sorted. The stored and displayed trait text is unchanged. Standard Chogs have no traits.
  - **Future resolver rules:** it sees only the game's catalog and the normalized traits (no wallet, token, room or match), and it is deterministic. When it names no ability of the catalog (a guest, or traits that map to nothing), the player gets the whole catalog, like the shared pool, so nobody is left unable to ready. Ids outside the catalog are dropped. The player still selects exactly one ability (NFT-016).
  - **Boundary:** game modules never mention characters, traits, the NFT namespace or the resolver, and the shared engine folders of Core (`Abilities`, `Games`, `Matches`, `Rooms`) never read traits; an architecture test scans the sources. Only an `IAbilityAssignmentStrategy` may read a character's traits.
- DEC-035 (2026-10-13, STORY-033 — confirmed by product owner): Lobby ability selection and lock.
  - **Choosing:** a member chooses with `PUT /api/rooms/{code}/ability {abilityId}`; the choice is stored on the member and kept when they withdraw ready. It must be an ability their pool offers for the Chog they have selected (`400 unknown_ability` otherwise, nothing changes). Ready counts only for the ability chosen when marking ready, so choosing another one makes the member not ready, as changing Chog does (DEC-022). After the start nothing can be switched (`room_started`).
  - **Ready:** in a game with abilities, ready needs a choice the pool offers (`409 ability_required`). A game without abilities (every game until its catalog ships) readies and starts without one, and its members have no ability.
  - **Visibility:** until the start, other members see only that a member has chosen (`hasAbility`), never which ability; the member sees their own choice. Once started, everyone sees every locked ability. Each member gets their own options in the room's `abilities` while it waits.
  - **Lobby pool:** the lobby asks the pool with the selected Chog as stored, without a chain call or traits; the shared pool doesn't read them. The start asks again with the live character snapshot, which is what counts.
  - **At start:** each choice is checked again. If the pool no longer offers it (a deploy changed the catalog), the start is refused with `409 ability_unavailable`, those members' choices are cleared and they are set back to not ready; nobody else changes. Otherwise each member's ability is locked as an `AbilitySnapshot` (id, catalog version, name, description, target, windows, parameters, max uses) in `RoomMembers.Ability`, in the start's transaction, and later catalog changes don't touch it (NFT-015, ADR-008). The used count comes with STORY-034.
- DEC-036 (2026-10-13, STORY-034 — confirmed by product owner): Ability execution and usage tracking.
  - **Routing:** `USE_ABILITY` (`{"abilityId": "...", "target": seat}`) goes to the shared `AbilityEngine` for every game, never to the game's `IMatchRules`, under the same room lock, replay, status, version, turn and deadline checks as other commands. A game without an ability catalog answers `unknown_command`. Engine refusals are `409 command_rejected` with the engine's or the handler's `reason`.
  - **Locked ability only:** a player can use only the ability they locked at start (`not_your_ability` for another of the game's abilities, `unknown_ability` for one the game doesn't have), at most its locked `maxUses` (`ability_used_up`). Uses are counted in `RoomMembers.AbilityUses`, in the command's transaction, and a database check keeps them between 0 and the locked max.
  - **Turn:** only the current player can use an ability, before their deadline. A use never ends the turn or the match; like any action it resets the player's missed turns. Reactions on other players' turns come with Chog Race (STORY-055).
  - **Catalog changes mid-match:** the effect uses the values locked at start (parameters, windows, target, max uses) and the game's current handler for that id. If the handler is gone or no longer accepts the locked parameters, the use is refused with `ability_unavailable` and nothing changes (NFT-015).
  - **Broadcast:** a use is announced like any applied command (`RoomUpdated`). Locked abilities in snapshots show `usesLeft`, and every member shows their `seat` so targets can be named; the effect is visible through the game state. There's no separate ability event.
- DEC-037 (2026-10-13, STORY-035 — confirmed by product owner): Chog Life rules configuration.
  - **Home:** the rules are versioned code in the Chog Life module (`LifeRules`, version 1 in `LifeRulesV1`), like the ability catalogs (DEC-032), not an appsettings section. They are checked when built, at API startup, so a malformed board stops the API. Any change means a new version; matches will record the version they started with when the game's rules plug in (STORY-037).
  - **Board:** 36 tiles on a main track with two Safe/Degen forks (tiles 9 and 25). Each fork splits into a short safe lane and a short degen lane that join the main track again at one tile, so every route is 29 tiles long. Tiles link forward by index: a branch to its two lanes, the finish to nothing, every other tile to one next tile. Checks: 30–40 tiles in index order, one Start first and one Finish last, forward links to existing tiles, every tile reachable, only a branch enters a lane, starts, finishes and branches on the main track, and both lanes of a fork joining at one tile.
  - **Values:** 100 MON to start (LIFE-002); +100 MON only for the first player to reach the finish (LIFE-007); a 20-minute time cap, never above 20 minutes (ENG-011, enforced with STORY-041); one six-sided die (1–6). MON are whole numbers.
  - **Tiles:** Start, Normal, Reward and Loss (a fixed amount of 1–1,000 MON), Event (a kind: market, airdrop, rug or liquidation), Branch and Finish. Event odds and outcomes come with STORY-038, branch payoffs with STORY-039. These are proposed defaults to balance in STORY-044.
  - **Off-chain:** MON are fictional game points (DEC-010). No game module references wallets, the network or crypto libraries, which an architecture test enforces, so no real token can move.
